# Critical Business Logic Review

Reviewed: 2026-08-12

Scope: configuration persistence, peer and exit-node validation, live WireGuard and policy-routing reconciliation, and BGP lifecycle management.

## Findings

### P1 — Strict routing can silently fail open

`Peer.Validate` treats any non-empty `ExitNodeID` as sufficient for strict mode, without checking that the referenced peer exists, is enabled, and is an exit node ([`internal/models/models.go:421`](internal/models/models.go#L421)). The routing generator only installs the exit-node lookup and final `prohibit` rule if the reference resolves ([`internal/routing/routing.go:66`](internal/routing/routing.go#L66), [`internal/routing/routing.go:84`](internal/routing/routing.go#L84)).

A stale form submission or malformed request can therefore save a peer as strict while its traffic falls through to the host's main routing table.

Status: **fixed** by store-level reference validation and fail-closed rule generation.

### P1 — Removed policy rules remain active in the kernel

`GeneratePostUpCommands` clears only priorities present in the new configuration ([`internal/routing/routing.go:220`](internal/routing/routing.go#L220)). Saving first overwrites `wg0.conf`, so a later Apply Config also runs `wg-quick down` with the new `PostDown` list rather than the rules that were previously installed ([`internal/handlers/export.go:83`](internal/handlers/export.go#L83)).

When the generated rule set shrinks, obsolete rules and routes are never removed. For example, disabling strict routing can leave the old `prohibit` rule active and continue blocking the peer.

Status: **fixed** by previous-to-next routing reconciliation. Policy-route teardown identifies routes by prefix and table, so cleanup remains correct immediately after startup even before ZeroTier interface metadata has been rediscovered.

### P1 — Automatic WireGuard reload fails under the production shell

`ReloadWGConfig` invokes `sh` but uses Bash process substitution, `<(...)` ([`internal/wireguard/wireguard.go:24`](internal/wireguard/wireguard.go#L24)). The production image is Alpine ([`Dockerfile:1`](Dockerfile#L1)), where this command is not valid for `/bin/sh`.

`Store.Write` logs the reload error and still returns success ([`internal/config/config.go:130`](internal/config/config.go#L130)). Configuration is persisted and the UI reports success, but the running WireGuard interface retains its old peer configuration.

Status: **fixed** with direct commands, preserved stderr/stdout, and typed live-apply failures.

### P1 — Partial BGP initialization is reported as healthy

The global `bgpSrv` is assigned before kernel route integration is initialized ([`internal/bgp/bgp.go:231`](internal/bgp/bgp.go#L231)). If `kernel.New` fails, `start` returns without clearing the partially initialized globals. Future calls see a non-nil server and skip initialization, while `GetBGPStats` reports `Running` solely from that pointer ([`internal/bgp/stats.go:47`](internal/bgp/stats.go#L47)).

The dashboard can therefore report a running BGP service even though learned routes cannot be installed in the kernel, and ordinary configuration saves do not retry initialization.

Status: **fixed** by publishing BGP state only after complete runtime initialization.

### P1 — BGP listener configuration is not reconciled or shut down

`Configure` restarts the server only when Router ID changes ([`internal/bgp/bgp.go:72`](internal/bgp/bgp.go#L72)). Changes to the BGP listen address or port leave the old listener active. The current `stop` implementation disposes peers and drops pointers but does not close the TCP listener ([`internal/bgp/bgp.go:256`](internal/bgp/bgp.go#L256)). The pinned `bio-rd` API does not expose a listener/server shutdown operation.

Disable/re-enable, Router ID changes, and listener changes can consequently leave an orphaned listener holding the old socket. New peer/listener failures are only logged, and `Configure` still returns success.

Status: **fixed** with restart-sensitive state tracking, a closeable listener manager, and propagated errors.

### P2 — Rejected ZeroTier edits are not rolled back

`Store.Write` deep-copies only `Peers`; `ZeroTier.Networks` remains shared with the rollback snapshot ([`internal/config/config.go:108`](internal/config/config.go#L108)). Updating an existing ZeroTier network mutates its slice element before validation ([`internal/handlers/zerotier.go:177`](internal/handlers/zerotier.go#L177)).

If validation rejects the edit, restoring the shallow snapshot keeps the rejected value in memory. A later unrelated successful save can persist it.

Status: **fixed** by cloning all mutable configuration slices before mutation and when handing desired network state to the asynchronous ZeroTier supervisor.

## Implementation Plan

Implement in this order so later phases build on reliable validation and state transitions.

### Phase 1 — Add regression coverage and safe configuration snapshots

- [x] Add focused tests for each finding before changing behavior:
  - missing or disabled strict exit-node reference is rejected and cannot generate a fail-open rule set;
  - removing strict/policy routing removes previously generated rules;
  - a rejected ZeroTier update leaves the stored network unchanged;
  - WireGuard reload executes without shell syntax;
  - failed BGP initialization leaves the service stopped and retryable;
  - listen address, port, ASN, and Router ID changes trigger the expected BGP lifecycle.
- [x] Add one `AppConfig.Clone` implementation that copies every mutable slice, including nested peer route/filter slices and `ZeroTier.Networks`.
- [x] Use that clone for `Store.Write` rollback and for the previous-versus-next configuration needed by routing reconciliation.
- [x] Validate exit-node references once at the configuration boundary after every mutation. Reject references to missing, disabled, or non-exit peers.
- [x] Make strict routing fail closed in `peerRules` as defense in depth, so a hand-edited invalid configuration cannot fall through to `main` before validation catches it.

Acceptance: invalid mutations leave both in-memory and on-disk configuration unchanged; strict mode never produces a fail-open ruleset.

### Phase 2 — Make WireGuard and policy routing converge together

- [x] Replace `sh -c "wg syncconf ... <(...)"` with two direct `exec.Command` calls: capture `wg-quick strip wg0`, then provide those bytes as stdin to `wg syncconf wg0 /dev/stdin`.
- [x] Preserve command output in returned errors and stop converting live-apply failures into successful saves.
- [x] Reconcile routing from the cloned previous configuration to the new configuration: apply the previous `PostDown` commands first, then the new `PostUp` commands.
- [x] If applying the new routing state fails, best-effort restore the previous `PostUp` state and return an explicit “saved/apply failed” error rather than claiming full success.
- [x] Route peer saves, ZeroTier gateway changes, and Apply Config through the same reconciliation function. Remove duplicate partial apply behavior once all callers use it.

Acceptance: create, edit, toggle, and delete operations update both WireGuard peers and kernel routing immediately; shrinking the rule set leaves no obsolete managed rules or routing-table entries.

### Phase 3 — Give BGP one transactional runtime owner

- [x] Replace the independent BGP globals with one small runtime value containing the server, VRF registry, kernel integration, listener manager, and the active server configuration.
- [x] Build a candidate runtime using local variables. Publish it as running only after kernel registration and server/listener startup succeed.
- [x] On any startup failure, dispose every initialized resource and leave the runtime nil so the next `Configure` call retries.
- [x] Compare all restart-sensitive server fields: Router ID, ASN, listen address, and listen port.
- [x] Add a real shutdown capability to the pinned `bio-rd` integration. Upstream still exposes no shutdown API, so wg-busy supplies the smallest closeable listener manager at the integration boundary.
- [x] Make peer add, replace, listener bind, and shutdown failures propagate from `Configure` instead of being logged as success.
- [x] Derive dashboard `Running` from a fully initialized runtime, not merely a non-nil server pointer.

Acceptance: BGP can be enabled, disabled, re-enabled, and rebound repeatedly without leaked sockets; failed initialization is reported as stopped and succeeds on a later retry when the cause is removed.

### Phase 4 — End-to-end verification and documentation

- [x] Run `go test ./...` and add focused coverage for command construction and closeable listener behavior.
- [x] In an Alpine container, verify peer create/update/delete, strict-mode removal, Apply Config, BGP bind changes, and BGP disable/re-enable; cover kernel-integration failure with an injected regression test.
- [x] Confirm the UI distinguishes “configuration persisted” from “live apply succeeded” wherever those outcomes can differ.
- [x] Update `DESIGN.md` to document the configuration transaction, managed-routing reconciliation, and BGP lifecycle ownership.

Acceptance: the full test suite passes, the container scenarios converge without stale rules or listeners, and no success response is emitted for a failed live apply.

## Recommended Change Sets

Keep the work reviewable as three commits:

1. `fix: validate and snapshot configuration safely`
2. `fix: reconcile live WireGuard and policy routing state`
3. `fix: make BGP lifecycle transactional`

Each commit should include its regression tests. Avoid introducing a general command framework or new persistence layer; small package-local seams for command execution and lifecycle testing are sufficient.
