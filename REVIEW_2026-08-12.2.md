# Critical Business Logic Review — 2026-08-12.2

Reviewed: 2026-08-12

Scope: persisted configuration, WireGuard startup and live apply, exit-node routing, BGP lifecycle, automatic address allocation, concurrent configuration reads, and ZeroTier process ownership.

## Findings

### P1 — Startup can use a missing or stale `wg0.conf`

Existing YAML is loaded but only rendered when the server key is missing. Startup then immediately runs `wg-quick up wg0`. Container recreation, manual YAML edits, or a custom `-wg-config` path can therefore start stale state or fail entirely. The custom path is also ignored by the hard-coded interface command.

Status: **fixed**. Startup now validates and renders the YAML source of truth, then restarts WireGuard using the configured file path.

### P1 — Server saves report success for fields `wg syncconf` cannot apply

Address, MTU, DNS, table, and lifecycle hooks are saved, but `wg-quick strip` removes those fields before `syncconf`. The live interface keeps its old settings while routing reconciliation assumes the new address.

Status: **fixed**. The store tracks wg-quick-owned fields against the last fully applied server state and returns `ApplyError` until Apply Config completes.

### P1 — Removing an exit node can blackhole strict clients

Cascading clears only `ExitNodeID`. A dependent strict peer with no policy routes is not revalidated, and routing then installs only its terminal `prohibit` rule, blocking all its traffic.

Status: **fixed**. Every store mutation now validates every peer, so an exit-node cascade that leaves a strict peer without a lookup is rejected and rolled back.

### P1 — Multiple full-tunnel exit nodes cannot be selected correctly

Every full exit node receives identical `0.0.0.0/0, ::/0` WireGuard AllowedIPs. WireGuard assigns each prefix to one peer, so the last rendered exit node captures traffic intended for the others. No cross-peer overlap validation prevents this.

Status: **fixed**. Full-config validation rejects duplicate effective WireGuard prefixes, including multiple full-tunnel defaults.

### P1 — BGP accepts peer configurations the runtime does not represent

`BGPPeerPort` is validated and persisted but never copied into runtime configuration, so active sessions always use the embedded engine's default port. Peers are also keyed only by BGP IP; duplicate addresses silently overwrite the earlier peer's ASN and filters.

Status: **fixed**. Peer port 179 is enforced explicitly and duplicate enabled BGP addresses are rejected at both configuration and runtime boundaries.

### P1 — BGP changes are skipped when `wg0` is down

`bgp.Configure` is inside the WireGuard-running branch. Disabling BGP while WireGuard is unavailable can leave the old listener/runtime active, while enabling it returns success without starting it or producing an `ApplyError`.

Status: **fixed**. BGP disable always runs; enabled BGP while WireGuard is unavailable now produces a live-apply error.

### P2 — Auto-IP allocation mishandles supported address lists

Server validation permits comma-separated and IPv6 CIDRs, but IPAM parses the entire server string as one CIDR and only walks IPv4. Existing peers with comma-separated addresses are also ignored, allowing duplicate IPv4 allocation.

Status: **fixed**. IPAM splits server and peer address lists, prefers the IPv4 pool on dual-stack servers, and supports IPv6-only allocation.

### P2 — Configuration pointers escape the store lock

Peer rendering retains `*AppConfig` after `Read` unlocks; ZeroTier rendering similarly retains a shallow network slice. Concurrent stats polling and configuration writes can race or render internally inconsistent state.

Status: **fixed**. `Store.Read` now provides a complete cloned snapshot that callers can safely retain.

### P2 — ZeroTier restart can overlap old and new processes

Shutdown sends `SIGTERM`, immediately forgets the process, and may start another daemon without waiting for the first to exit. Both use the same home directory, producing intermittent restart or port-change failures.

Status: **fixed**. The supervisor detaches and waits for process exit, with a bounded SIGKILL fallback, before starting a replacement.

## Implementation Plan

1. Always validate and render the persisted configuration before starting WireGuard. Pass the configured `wg0.conf` path to every `wg-quick` operation.
2. Track server fields that require a full restart and return a persisted-but-not-live `ApplyError` until Apply Config completes.
3. Validate the complete peer set at the store boundary, including strict dependents, full-tunnel exit-node collisions, unique BGP peer IPs, and the currently supported BGP peer port.
4. Apply BGP disable independently of WireGuard state; report enabled-but-unstartable BGP as a live-apply failure.
5. Make IPAM split address lists and allocate from either an IPv4 or IPv6 subnet without forgetting existing multi-address peers.
6. Return cloned configuration snapshots from read operations so callers cannot retain mutable store state.
7. Wait for ZeroTier process exit with a bounded kill fallback before starting a replacement.
